# Space Daily — starter website

A separate, static-first, mobile-friendly concept website. Independent of Atlas of the Cosmos.

## Open it

1. Open this folder in VS Code or Codex.
2. In a terminal here, run `python -m http.server 8000`.
3. Open `http://localhost:8000` in your browser.

The daily lesson, quiz, topic preferences and UI work immediately. NASA news and gallery cards populate from the shared content cache. The initial cache is deliberately empty rather than filled with invented live news.

## Import NASA content

Run `python refresh_content.py` with internet access. It fetches NASA RSS headlines, official article preview images, Image and Video Library thumbnails, and the current Astronomy Picture of the Day into `data/latest.json`. Each image URL is restricted to NASA hosts and checked for an image response before it enters the cache; a failed refresh retains the previous valid cache. Then refresh the website. You can set up a GitHub repository and enable Actions; the supplied workflow refreshes daily. GitHub Pages can host this static site.

### NASA API key

The current sources are public. Space Daily uses `NASA_API_KEY` only as an optional server-side environment variable; it is never printed, stored in `data/latest.json`, or sent to browser code. The new APOD WordPress endpoint does not require a key. If a future NASA source requires a key, set `NASA_API_KEY` locally and add it as a GitHub Actions secret with the same name; never commit it.

## Data sources

- NASA News Release RSS: headlines, dates, links, and summaries.
- NASA article pages: their official social-preview image, when available.
- NASA Image and Video Library: gallery and curated learning imagery, with source links and credited creators.
- NASA APOD WordPress API: `https://science.nasa.gov/wp-json/wp/v2/apod-basic` for the daily image feature. The retiring `api.nasa.gov/planetary/apod` endpoint is not used.

## What is a prototype, not live?

- The Kit newsletter form is live. Scheduled automation is deliberately disabled: GitHub Actions only generates local preview artifacts unless a future, explicit delivery activation is completed.
- User accounts and synced bookmarks are **not implemented**.
- Topic selections are stored locally in the browser; they provide lightweight recommendations from the cached articles and reviewed lesson catalogue, not a personalised news feed.
- No analytics/tracking is installed.
- The illustrated hero and Moon are CSS art, not NASA photographs.
- NASA headlines link to their sources; the introductory lunar lesson is editorial sample content.

## Local content and lessons

`data/lessons.json` is a reviewed, version-controlled introductory sequence. It is separate from APOD and is not generated by the content-refresh script. Each lesson links to a NASA source and supplies its own quiz, source, and image credit.

The refresh script avoids repeated requests after a successful UTC-day refresh. For a deliberate local refresh, set `SPACE_DAILY_FORCE_REFRESH=1` in your shell for that one command.

## Newsletter automation

`newsletter.py` creates responsive Daily and Weekly HTML editions from the public NASA cache, APOD and reviewed lesson catalogue. It uses a small, public NASA-news history (`data/newsletter-history.json`) so the weekly edition can select stories from the prior seven days. Subscriber data is never written, committed, or logged.

Safe defaults:

- `python newsletter.py --edition both --mode preview` creates local files under `build/newsletters/` only.
- Preview generation skips an edition if its cache is stale or it has fewer than three valid, non-duplicate NASA stories.
- `.github/workflows/newsletter.yml` refreshes NASA data before producing preview artifacts at approximately 09:00 Asia/Kolkata (`03:30 UTC`); GitHub scheduling may be delayed.
- The workflow supports an explicitly triggered read-only `verify` mode to check tag IDs. It cannot create drafts or send email.
- `.github/workflows/kit-test-newsletter.yml` is manual-only and cannot send or create a broadcast. It prepares a Daily preview, resolves only the exact `Space Daily Test` tag, and stops unless Kit returns exactly one active recipient. It does not print or save recipient identity data.

Kit V4 draft/test/production commands are deliberately not in the workflow. They require `KIT_API_KEY`, an HTTPS `SPACE_DAILY_SITE_URL`, the exact Kit tags `Daily Newsletter` and `Weekly Newsletter`, and separate environment approval tokens enforced by the script. The production path targets only the matching Kit tag and detects an existing broadcast marker before creating another.

Required GitHub configuration before any future Kit verification or delivery:

- Secret `KIT_API_KEY` — a Kit API V4 key; never commit or expose it.
- Secret `NASA_API_KEY` — only if a future NASA source needs it.
- Variable `SPACE_DAILY_SITE_URL` — the future public HTTPS site URL; delivery refuses to run without it.
- For an approved test only: secret `NEWSLETTER_TEST_SEND_ENABLED` with `I_APPROVE_TEST_SEND`. `KIT_TEST_TAG_ID` is optional but, if set, must match the ID resolved from the exact `Space Daily Test` tag.
- For production only: secret `NEWSLETTER_PRODUCTION_ENABLED` with `I_APPROVE_PRODUCTION_SENDING`.

Do not add the two delivery approval secrets or wire a delivery workflow until the preview, Kit tag verification, sending address, confirmation behaviour and a test-only audience have been reviewed.

### Controlled Kit test verification

After this repository is pushed and `KIT_API_KEY` is configured as a GitHub Actions secret, manually run **Verify controlled Kit newsletter test**. It is not scheduled and is read-only: it produces a Daily HTML preview artifact and verifies the `Space Daily Test` tag ID plus its active-recipient count. A result other than exactly one stops the workflow before any send-related operation. The workflow deliberately has no input, permission, or command for sending a newsletter.

### Sending the one-recipient test

`.github/workflows/kit-send-test-newsletter.yml` is manual-only and has no schedule. It is protected by all of the following: the `SEND_ONE_TEST_EMAIL` dispatch choice, the protected `kit-test-send` environment, an environment-scoped `NEWSLETTER_TEST_SEND_ENABLED` secret set to `I_APPROVE_TEST_SEND`, and a minimum 15-minute scheduled-send lead time. Immediately before scheduling, it resolves the exact `Space Daily Test` tag again, rejects a clash with the Daily or Weekly tags, and requires exactly one active recipient. It also requires an explicit `KIT_TEST_SENDER_EMAIL` environment variable and passes that value to Kit rather than accepting the account default. The rendered HTML retains Kit's `{{ unsubscribe_url }}` merge tag.

Before approving a send, create the `kit-test-send` GitHub environment with at least one required reviewer. Add environment secrets `KIT_API_KEY` and `NEWSLETTER_TEST_SEND_ENABLED`; add environment variables `KIT_TEST_SENDER_EMAIL` (a sender already verified in Kit) and `SPACE_DAILY_SITE_URL` (the future HTTPS site URL). The test workflow explicitly supplies that sender to Kit and checks that Kit echoes it in the broadcast response. Invalid credentials or insufficient broadcast permission stop the API request; verify the sender in Kit before approving. Do not configure the approval secret until you are ready to perform this one test.

## GitHub workflow safety

The repository is connected to GitHub, but no deployment or GitHub Pages configuration is included. The refresh and preview workflows can update only public NASA cache data and preview artifacts; neither workflow sends subscriber email.
